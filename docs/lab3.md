# ЛР3. Базовый каркас приложения, Clean / Layered Architecture, настройка окружения

Вариант 5 — Carsharing / Rental API. Стек: Python 3.12, FastAPI, Pydantic Settings, pytest.

## 1. Структура проекта

```
app/
├── main.py               # create_app(): настройки → логирование → хранилища → middleware → роутеры
├── __main__.py           # запуск через `python -m app`, хост и порт из HTTP_HOST / HTTP_PORT
├── api/                  # слой API (HTTP)
│   ├── health.py         # GET /health и GET /api/v1/health
│   ├── v1/router.py      # префикс /api/v1
│   ├── v1/vehicles.py    # эндпоинты автопарка
│   ├── deps.py           # сборка зависимостей через Depends (DI)
│   ├── errors.py         # единый ErrorResponse, доменные исключения → HTTP-коды
│   └── middleware.py     # request_id для каждого запроса
├── services/
│   └── vehicle_service.py      # бизнес-правила автопарка
├── repositories/
│   └── vehicle_repository.py   # интерфейс VehicleRepository + InMemoryVehicleRepository
├── models/vehicle.py     # доменная сущность Vehicle и статусы
├── schemas/              # Pydantic-схемы запросов и ответов (по openapi.yaml)
└── core/
    ├── config.py         # Settings: переменные окружения с префиксом APP_ и файл .env
    ├── exceptions.py     # NotFoundError, ConflictError — без привязки к HTTP
    └── logging.py
tests/                    # 27 тестов: конфигурация, сервис без HTTP, API
```

Соответствие примеру структуры из задания (там пример в стиле Go):

| Пример из задания | В проекте (Python) | Слой |
|---|---|---|
| `cmd/app/main.go` | `app/__main__.py`, `app/main.py` | Точка входа |
| `internal/config/` | `app/core/config.py` | Загрузка конфигурации из `.env` |
| `internal/controller/` | `app/api/` | Transport / HTTP Handlers |
| `internal/service/` | `app/services/` | Business Logic Layer |
| `internal/repository/` | `app/repositories/` | Data Access Layer |
| `.env.example`, `.gitignore`, `openapi.yaml`, `ARCHITECTURE.md`, `README.md` | те же файлы в корне | — |

Дополнительно: `app/models/` — доменные сущности, `app/schemas/` — схемы запросов и ответов, `tests/` — тесты.

Слои зависят только «вниз»: `api → services → repositories`. Сквозной пример, проходящий через все слои, — управление автопарком `/api/v1/vehicles` (список, создание, получение, изменение, списание). Данные пока хранятся в памяти; PostgreSQL подключается в ЛР5–6.

## 2. Конфигурация окружения

- Все настройки описаны в модуле `app/core/config.py` (класс `Settings` на `pydantic-settings`) и читаются из переменных окружения: `APP_NAME`, `APP_ENV`, `HTTP_PORT` и т. д. Значения проверяются при старте: например, `HTTP_PORT=abc` не даст приложению запуститься.
- Для локальной разработки значения можно положить в файл `.env` — переменные окружения имеют приоритет над ним.
- В репозитории лежит шаблон [`.env.example`](../.env.example) со всеми переменными и комментариями. Файл `.env` указан в [`.gitignore`](../.gitignore) и в Git отсутствует:

```
$ git ls-files | grep env
.env.example
```

Полный список переменных — в [README](../README.md#переменные-окружения).

## 4. Ответы на контрольные вопросы

### 4.1 Почему слой бизнес-логики (Service Layer) не должен знать о деталях HTTP-запросов?

Правила предметной области не зависят от того, как пришёл запрос. «Нельзя списать автомобиль в аренде» — правило бизнеса, а не HTTP. Если сервис принимает `Request`, читает JSON-тело или заголовки, он привязывается к одному транспорту, и появляются проблемы:

- **Повторное использование.** Тот же `VehicleService` должен вызываться из REST-обработчика, из фоновой задачи Celery (истечение резерва), из CLI или gRPC. Если внутри сервиса разбор HTTP, во всех этих местах логику придётся дублировать.
- **Тестируемость.** Сервис без HTTP проверяется обычными unit-тестами: в `tests/test_vehicle_service.py` бизнес-правила тестируются без сервера и без запросов.
- **Устойчивость к изменениям.** Переименовали поле JSON, сменили фреймворк или версию API (`/v1` → `/v2`) — меняется только слой API, бизнес-логика не трогается.
- **Разделение ответственности.** API разбирает и валидирует запрос, выбирает код ответа. Сервис решает, можно ли выполнить операцию.

Как в проекте: роутер `app/api/v1/vehicles.py` превращает тело запроса в обычные аргументы (`service.create_vehicle(**body.model_dump())`). Сервис возвращает доменный объект или бросает `ConflictError` / `NotFoundError` из `app/core/exceptions.py`. Про коды 404 / 409 сервис не знает: перевод в HTTP делает `app/api/errors.py`.

### 4.2 В чём опасности хранения секретов (пароли к БД, API-ключи) прямо в исходном коде?

- **Утечка через репозиторий.** Код видят все, у кого есть доступ к Git: коллеги, подрядчики, CI, а при публичном репозитории — весь интернет. Боты автоматически сканируют GitHub в поисках ключей.
- **Секрет остаётся в истории.** Даже если удалить пароль из файла, он сохранится в старых коммитах. Тогда секрет нужно отзывать и менять, а историю — переписывать.
- **Одни и те же секреты во всех окружениях.** Если пароль зашит в код, для dev и prod он один и тот же. Утечка с ноутбука разработчика открывает боевую базу.
- **Смена секрета — это релиз.** Чтобы поменять ключ, приходится менять код, собирать и выкатывать новую версию вместо простой смены переменной.
- **Нет разграничения доступа.** Кто читает код, тот знает все пароли, хотя разработчику не нужен доступ к боевой БД.

Правильно (принцип 12-factor app «Config»): секреты передаются через переменные окружения или хранилище секретов (Vault, Kubernetes Secrets, секреты CI). В коде — только чтение настроек. В проекте все настройки читаются в `Settings` из переменных `APP_*`, а `.env` с локальными значениями не коммитится.

### 4.3 Зачем нужен файл `.env.example`, если сам `.env` находится в `.gitignore`?

`.env` не попадает в Git, потому что в нём реальные значения и секреты. Но тогда новый разработчик или сервер CI не знает, какие переменные нужны приложению. `.env.example` решает эту задачу:

- **Документация конфигурации.** Список всех переменных с комментариями и безопасными значениями по умолчанию.
- **Быстрый старт.** `cp .env.example .env` — и проект запускается локально без расспросов коллег.
- **Шаблон для окружений.** По нему DevOps заполняет переменные на сервере, в Docker или CI.
- **Контроль изменений.** Добавили новую переменную — она появляется в `.env.example` и видна в код-ревью.

В `.env.example` никогда не кладут настоящие пароли и ключи: только заглушки или значения для локальной разработки.

### 4.4 Для чего в микросервисной и серверной архитектуре используется эндпоинт Health Check (`/health`)?

Это быстрый ответ на вопрос «сервис жив и может обслуживать запросы?». Его вызывают не пользователи, а инфраструктура:

- **Балансировщик нагрузки** (Nginx, облачный LB) перестаёт отправлять трафик на экземпляр, который не отвечает или отвечает ошибкой.
- **Оркестратор** (Kubernetes, Docker): liveness probe перезапускает зависший контейнер, readiness probe не пускает трафик, пока сервис не готов (например, ещё не подключился к БД).
- **Мониторинг и алерты** (Prometheus, Uptime Kuma, Zabbix) регулярно опрашивают эндпоинт и поднимают тревогу при сбое.
- **Деплой.** Новая версия считается успешно выкаченной, только когда её health check отвечает 200; иначе — откат.
- **Service discovery** в микросервисах исключает нездоровые экземпляры из реестра.

Health check работает без авторизации и должен отвечать быстро. В проекте `GET /api/v1/health` (и `/health`) возвращает 200 со статусом `pass`, названием сервиса, версией, окружением и временем работы. По спецификации при недоступности зависимостей (БД, Redis — после ЛР5) он будет отвечать 503.

### 4.5 Что такое инверсия зависимостей (Dependency Inversion) и как она помогает связывать слои API, сервисов и репозиториев?

**Принцип инверсии зависимостей** (буква D в SOLID):

1. Модули верхнего уровня (бизнес-логика) не должны зависеть от модулей нижнего уровня (БД, внешние API). Оба зависят от абстракции.
2. Абстракции не должны зависеть от деталей; детали зависят от абстракций.

Без инверсии сервис сам создаёт подключение к PostgreSQL и становится к нему привязан. С инверсией сервис объявляет, что ему нужно, — интерфейс, а конкретную реализацию передают снаружи.

Как это устроено в проекте:

```python
# app/repositories/vehicle_repository.py — абстракция
class VehicleRepository(ABC):
    def get(self, vehicle_id: UUID) -> Vehicle | None: ...
    def add(self, vehicle: Vehicle) -> Vehicle: ...

class InMemoryVehicleRepository(VehicleRepository): ...   # деталь (сейчас)
# class PostgresVehicleRepository(VehicleRepository): ... # деталь (ЛР6)

# app/services/vehicle_service.py — сервис знает только интерфейс
class VehicleService:
    def __init__(self, repository: VehicleRepository) -> None:
        self._repository = repository

# app/api/deps.py — внедрение зависимостей (Dependency Injection) через FastAPI
def get_vehicle_service(repository = Depends(get_vehicle_repository)) -> VehicleService:
    return VehicleService(repository)
```

Что это даёт:

- **Слои связаны через интерфейсы, а не через конкретные классы.** Роутер получает готовый `VehicleService` через `Depends`, сервис получает репозиторий через конструктор. Никто не создаёт свои зависимости сам.
- **Замена хранилища без правок логики.** В ЛР6 вместо `InMemoryVehicleRepository` подключается репозиторий на PostgreSQL — меняется одна строка сборки в `app/main.py`, сервис и API не трогаются.
- **Тестирование.** В тестах сервису передаётся репозиторий в памяти, и правила проверяются без БД (`tests/conftest.py`).

Dependency Inversion — это принцип (от чего зависеть), а Dependency Injection — способ его реализовать (кто и как передаёт зависимость). В FastAPI для DI используется `Depends`.
